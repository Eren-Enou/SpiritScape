# v0.40: Release candidate

Thirty-one milestones were built on top of each other as stacked pull requests, and `main` is still at v0.8. This branch gathers all of them into one candidate that can be reviewed against `main`, adds automated checks, fixes the defects found while doing that, and makes the game easy to start and test.

**Nobody has played any of this.** Everything below is automated.

## Integration plan

### What's in the candidate

`v0.40-release-candidate` starts from `v0.39-ice` and adds only fixes, CI, launchers and documentation. There are no new features.

- **All 31 open pull requests (#7 to #37) form one linear chain:** #7 targets `main`, and each later PR targets the one before it.
- **Every PR's head commit is an ancestor of `v0.39-ice`,** which is 38 commits ahead of `main`. Nothing is missing, duplicated or conflicting, and no rebase was needed.
- **`main` is an ancestor of the candidate,** so it merges with no conflicts.

### How to merge

1. Review the consolidated PR from `v0.40-release-candidate` into `main`.
2. **Merge it with "Create a merge commit"**, not squash or rebase. That keeps all 38 milestone commits and their history.
3. GitHub will then show #7 as merged, because its commits will be in `main`.
4. PRs #8 to #37 target the branch before them, not `main`, so they'll stay open. Once you're happy, close them as included in the consolidated PR. Their branches can stay as a record.

I haven't closed, merged or changed any of them.

### Work that isn't in the candidate

Seven later milestones (v0.40 to v0.46, plus an unfinished v0.47) were built but never published. They're on local branches named `wip/v0.40-what-they-leave` through `wip/v0.47-in-progress`. They add new features, so they're left out of this candidate. The defect fixes from them are included.

### Scripted UI tests

**All 36 pass,** run one at a time on this machine against the release build.

Six of them changed, because saving inside a scenario now goes to the scenario's own folder and says so: "Scenario saved. Your own game's save is untouched." They used to expect "Game saved". Each of them still saves, loads with `F9` and checks the game came back.

**Run nothing else heavy while they run.** They're timed in seconds, and two sets at once, or a big build alongside them, made sound scripts fail during this work.

## CI

`.github/workflows/ci.yml` runs on every pull request, on pushes to `main` and `v0.*` branches, and by hand.

- **Checks job:** formatting, Clippy with warnings as errors, and every workspace test. Those include the save-compatibility fixtures, deterministic replay and save/load hash checks, and resource and XP conservation.
- **Long-runs job:** the 8 release-only whole-game tests, and the reference game report.
- **Not on CI: the scripted UI tests.** They open a real window and need a GPU, which hosted runners don't have. Run them locally with the scratch `runui.sh`, or by hand with the command at the top of each `scripts/ui_*.txt`.

**The first run passed:** both jobs succeeded on pull request #38, on Linux, in about 20 minutes. That covers formatting, Clippy, all 590 workspace tests, the 8 long runs and the reference game report.

## Save compatibility

- **The save format is 9.** Formats 1 to 8 are migrated on load, and the original file is kept beside it as `.vN`.
- **Every write keeps the previous save as a backup.** A damaged save falls back to that backup, and a newer format is refused with a message, never misread.
- **Fixtures written by older versions load in the tests:** v1 to v8, covering a journey, panels, a road, a crossing and a yard.
- **Covered by tests:** saving and loading in every scenario, with resources and XP conserved; mid-construction; outposts; named spirits; a visitor waiting for an answer; on the ice in winter; part-way through the Still Boat; and after either ending.
- **New:** a test saves and reloads every few steps all the way through the Still Boat, and the XP comes back exactly once.

Nothing was tested against your own saves, which these checks never touch.

## Defects found and fixed in this candidate

1. **Quarrying, Masonry and Kiln Spirits were invisible.** Quarrying Spirits had been invisible since v0.15, Masonry since v0.24, and Kiln since v0.35. They worked and appeared in every panel, but had no body on the map and no name over their head. The game silently skipped any role without a model. All three now have bodies, a role without one falls back to the player's model, and tests check that every role, tree and building has visuals.
2. **Saving in a test scenario overwrote your real game.** Save wrote to the same `world.save` whether you were in your own game or a scenario, and Continue then loaded the scenario. Scenarios now save in `scenarios\<name>` inside the save folder.
3. **Returned XP was counted as earned.** The Still Boat's XP went through the same path as XP from work, which overstated what you'd earned in the play report. It now has its own column, `xp_returned`. The save format is unchanged, and older saves read it as zero.
4. **Clay Banks were announced hours before any clay existed,** as "Clay Bank: in . 6 Clay each" at Quarrying level 3. Anything listing what a skill can work on now only counts what's on the map.
5. **Words that assumed everything was wood:** a Kiln Spirit was "sawing", the quarry card said "Logs/min", and a Quarrying Spirit with stone said "No storage has room for more logs".
6. **A crash I introduced while making this candidate,** and caught before committing. A fix script ran twice and duplicated three entries in `data/visuals.toml`, so the game wouldn't start, while every headless test still passed. A new test now reads that file the way the game does.

**Tests added:** 4 for visuals, 1 for clay, 3 for the Still Boat's XP, 2 for scenario saves, and 1 for reading the visuals file.

**Tests changed:** one, because the session report now says "Waiting for regrowth" rather than "Waiting for trees". Seven UI scripts also changed: one for "on production" rather than "on planks", and six that save inside a scenario.

## The Still Boat: a deliberate exception, for your decision

SpiritScape began with one rule: you earn XP, sacrifice it to make a permanent spirit, and retrain while the settlement benefits. **The Still Boat breaks that rule on purpose.** Calling the spirits home gives back every point of XP they were made from, and they're gone.

**What I verified:**

- **XP comes back exactly once.** That holds with saving and loading between every few steps, and nobody can be called twice.
- **Spirits made after the boat leaves can't be called home,** so their XP stays given.
- **Spirits you never made** (the starting builder and hauler) have nothing to return, and leave anyway.
- **Conservation holds:** starting XP + earned + returned = current + separated.
- **Both endings survive saving and loading,** and so does doing both, in either order.

**What it means for play:** a player who builds the boat late can finish with nearly all their levels back. That's the point of the choice: you get yourself back, and lose the spirits. But it changes what a sacrifice means. If a player knows the boat is coming, the early sacrifices feel less permanent.

**This needs your decision:** keep it as it is, limit it (for example, return only part of the XP), or remove it. I haven't changed it.

### Other design changes since v0.8 worth your attention

These are design choices, not defects:

- **Spirits can't cross to the Far Shore,** and only the player can cut Stillwood.
- **"Leave your load":** when storage is full, you can drop what you're carrying. It keeps Woodcutting 20 reachable, but it's a workaround.
- **Tips open the interface gradually,** so a new game shows little at first.
- **Visitors' offers are small:** taking all six saves about 2 minutes in a 17-hour game.
- **Winter costs about a fifth of the reference game's time.**
- **The frozen river lets you reach the Far Shore 90 minutes in,** long before the crossing is built.

## Remaining technical risks

- **Physical mouse and keyboard have never been tested by a person.** The scripts send the same input messages, but nobody has played with real hands.
- **Window sizes:** the UI scripts all run at 1600×920. Smaller windows may crowd the right-hand panel, which scrolls.
- **CI runs on Linux, and the game is played on Windows.** The simulation is the same, but CI doesn't build the Windows executable.
- **Performance:** about 60 frames a second on the busiest map on this machine, capped by vsync. It hasn't been measured on other hardware.

## Economic evidence, without changes

From the deterministic reference players. I haven't changed any balance on this evidence, because these are design questions:

- **Winter costs about 3½ of 17 hours,** and holding more logs recovers about 1½ of them.
- **Resources pile up:** the reference game leaves over 2,300 units behind by the end.
- **Visitors' offers make little economic difference.**
- **There's no stretch longer than about 1 hour 10 minutes** without something new for the reference player. A person will be slower.

## Windows launch

From the repository root:

- **`play.bat`** builds the game if needed, then starts it. Anything you add goes to the game, for example `play.bat --new-game`.
- **`scenarios.bat`** shows a numbered list of 11 scenarios, and starts the one you pick. Scenario saves go to `%APPDATA%\SpiritScape\scenario-tests`.
- **`tools\package_windows.ps1`** makes a folder you can copy and play from without Rust installed.

Your own game is always in `%APPDATA%\SpiritScape`. If the game stops with an error, the window stays open to show it.
